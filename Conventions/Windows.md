# Windows

The Windows conventions of DynALisp, part of the [DynALisp Conventions](../CONVENTIONS.md): read before changing a window (WPF or DCL), its picture in the docs or the Manager. When a new convention of this topic is agreed, add it here, with the reason for it.

- The windows of DynALisp are **WPF windows**, shown by `DynALisp.Windows.dll` (`Installer\Windows`): each one a `.xaml` file of the `Res` folder of its module, without code, its controls named by their key (`x:Name`), what they do said by the `dyl:Win.*` properties (`Engine\Win.cs`: rules, sub-windows, docs page). The Lisp shows it with `(Dyl:WinShow file vals)` (Windows region of `dynalisp.mnl`) and gets back the button that closed it with the value of every key:
  - A new window is a `.xaml` file, never a `.dcl`. A DCL window moved to WPF loses its `.dcl` and its DCL functions: no copy is kept, since DynALisp needs AutoCAD 2015 (the oldest the plugin loads in).
  - Nothing calls the Lisp back while a window is open: a button that must run Lisp closes it with its number (`dyl:Win.Close`), and the caller opens it again on the values it got (as `c:Dyl-Settings`). The Manager, modeless, runs the Lisp of that button at the command line instead, with the same values (see the Manager below).
  - Its look is the theme of the plugin (`Engine\Theme.xaml`), in the colours of the light or dark theme of AutoCAD (`COLORTHEME`, the `Dyl.*` brushes of `Theme.Brushes`): a section is a `GroupBox` (a card without border), an on/off setting a `CheckBox` (drawn as a switch, but in the rows of a list, a small square box, `Dyl.Check`; its description indented under its label; greyed out, it is drawn off whatever its value, which is kept for when it is enabled again, so a setting not used never looks on), its description a `Dyl.Desc` text, keyed styles and brushes always as `{DynamicResource ...}`, never a colour written in the window file.
  - Its picture in the docs is drawn by `Installer\Windows\Shots`, without AutoCAD, never taken by hand: a window added or changed gets its row in `Shots.csv` and its sample values in `Samples\`, in the same change. The `Windows` workflow draws them on each push of a work branch that changes a window and commits those that changed to it: pull before pushing again.
  - A rule of a window file (`dyl:Win.EnabledBy`, `VisibleBy`) tests checkboxes (`key`, `!key`) and values (`key=a|b|`, `key!=a`, a trailing `|` for the empty value), joined by `,` (all) or `;` (any); a list tests the value stored for its item (`key/vals`), never its index. A rule greys out a whole row (its `DockPanel`), so its label greys out with its box. A text box is checked by `dyl:Win.Check` (`empty;integer;min=3`, `positive`, `widths`, `color`...), its message in `dyl:Win.CheckMessage`.
  - A plain list (`ListBox`, `key/list`) shows the columns of its items, divided by a tab as in a DCL `list_box`, in a template with `dyl:Cell.Converter` (`ConverterParameter` the column), never in one text; `dyl:Win.Close="n"` on it makes an item double-clicked close the window as its Run or OK button. A window shown by several commands (the child picker, `Res\Dyl-ChildPicker.xaml`) names a page no file has (`dyl:Win.Docs="child"`) and the Lisp gives its target (`docs/child`).
  - What the actions of a DCL list did runs in the window, with no call to the Lisp: the item picked fills the boxes under it (`dyl:Win.Fills="var:0,val:1"`, its columns, shown in the list or not), a search box filters it as it is typed (`dyl:Win.Filter="lst:0,2"`: every word typed, accents, ligatures and case ignored; the list still gives the indexes in all its items) and a text counts the items listed (`dyl:Win.CountOf`, `dyl:Win.CountText`); a list of several items (`SelectionMode="Extended"`) gives the indexes selected, `"0 3 5"`, as a DCL `list_box`; a list (or a text) that shows what each item has of the item picked in another list follows it (`dyl:Win.ItemsBy="rev"`, the Lisp giving its items for each one in `key/by`: the sheets of a revision). A list picked that changes what the Lisp shows (another profile, another dictionary) closes the window with its number (`dyl:Win.Close` on a `ComboBox`), and the Lisp shows it again on the new choice. A name asked (a new profile) is `Res\Dyl-Name.xaml`, shown again with why the name typed was refused (`error`).
  - A window that lists presets and edits the one shown is a **preset window** (`Engine\Presets.cs`): its list is a `ListBox` named `lst`, the Lisp gives its presets as a table (`pst/rows`, a list of rows) and gets them back as edited, with the aliases (`Remote>>Dyl:PresetWin`). The list, the selection, New, Copy, Delete, the resets and the aliases run in the window, with no call to the Lisp; the Lisp checks the presets again before it saves them. A preset tool is shown in WPF by a `.xaml` and `(window . "<file>.xaml")` in its spec (every preset tool: Quick Draw, Assembly Presets, Quick Shape, Materials, Hatch Presets).
  - A window that edits a list of rows (the layers of an assembly, the groups) is a **list of rows** (`Engine\Rows.cs`): a `ListBox` with `dyl:Win.Rows="1"`, the Lisp gives the rows as a table (`k/rows`, with `k/new` the row Add starts from and `k/defs` those of Reset) and gets them back as edited. Its fields are bound to the columns (`dyl:Win.Column`) and Add, Remove, Move up, Move down, Flip and Reset run in the window (`dyl:Win.Do`), with no call to the Lisp; a field changed goes to every row selected its rules hold for, and the Lisp checks the rows again before it gives them back. A sub-window on the rows (the Band Settings of a layer) is opened by the window itself (`dyl:Win.Open` with `dyl:Win.Columns="men:7,..."`): it edits the columns of the rows selected as its own keys; the same button outside a list of rows in a preset window edits the columns of the presets selected (the Border lines of an assembly). A list field can list only the items of the group of another field of the row (`dyl:Win.ListBy="lg"`, `key/by` the group of each item: the materials of a layer by their group), the group changed giving the row the first item of the new group. A checkbox in the template of the list sets the column of its own row (`dyl:Win.Toggle="n"`, shown with `dyl:On.Converter`, a small box `Dyl.Check`), as its field does; a column on in one row at most is greyed out in the others while one has it (`dyl:Win.Exclusive="lock"`, `{Binding Free[n]}`). A list with columns of checkboxes keeps them narrow under an abbreviation, named in a legend under the list (*LB  Load-bearing*). A preview of the rows (an `AssemblyTile`, `Engine\Assembly.cs`) is drawn again on each change. In a preset window, a list of rows can edit a column of the preset shown (`dyl:Win.RowsIn="3"`: rows divided by a new line, cells by a tab): it is loaded again when another preset is shown and written back to the preset after each change, greyed out while several presets are selected (`pst.many`), and the preset window checks it with its presets. A list of the preset window that picks another preset (the assembly of a Quick Draw preset) can give other columns with it (`pst/follow` `"38:42,44"` and the table `pst/follow/rows`), so the preview and the width follow the pick at once. The Lisp of the preset tool reads the rows back (`'wget`) and checks each preset changed (`'rowcheck`) before it saves them. A preset window **writes nothing when nothing changed** (its presets and aliases as they were read, `pst:lst0`, `pst:als0`: no file written, no alias or dynamic command defined again), and a preset given back as it was sent is the preset read, never cut and rebuilt (`Remote>>Dyl:PresetWinBack`). A tool whose rows take long to make gives `'wctx` (the values its rows depend on): the rows of the same list in the same context are made once (`*pst:rowcache*`).
  - The windows that set up the drawing tools are the **tabs of one window, the Manager** (`Dyl-Manager`, `Remote\Dyl-Manager.lsp`): Quick Draw, Assembly Presets, Quick Shape, Materials, Hatch Presets. Each tab is the window file of its tool as it is, run by its own Lisp; the Manager lists it in `*dyl:mgrtabs*` and `Dyl:WinShow` gives the tabs (`tab/list`, `tab`) to that window only, never to a window opened from it (Materials opened from Quick Draw stays a sub-window that gives back what was picked). Another tab picked closes the window with code 90 (`*dyl:wintabcode*`, `Engine\Tabs.cs`): the tool **saves** what was edited, as its Save (nothing when nothing was edited), and the Manager shows the next tab at the same place and size (`tab/place`). The Manager is **modeless**, so the user draws while it is open (`Modeless` of `Engine\Tabs.cs`, `tab/event`): `Dyl:Window` shows it and returns nil at once, and a button that needs the Lisp (another tab, Save, Draw, an open button) leaves it open, disabled, and runs its event at the command line (`(Remote>>Dyl:ManagerEvent key tab)`, the command running cancelled first): the Lisp of the tab runs again, and its `Dyl:Window` of that window gets the button and the values of the window, as from a modal one, so the Lisp of each tool stays the same. The window the Lisp shows next replaces it at the same place, drawn before the one left closes; `Dyl:WindowDone` closes it when the Lisp shows none. Draw puts it away while drawing and shows it again on its tab. A window opened from a tab stays modal. The main command of each tool opens the Manager on its tab. A new window that sets up a drawing tool is a tab of the Manager (a row of `*dyl:mgrtabs*`), not a window of its own.
  - A window **fits the screen and grows with its lists** (`Engine\Fit.cs`, applied to every window shown over AutoCAD): it opens at the size of its file, never larger than the work area of the screen (its lists shorter, the rest scrolling); a window with a list (a `ListBox`, a `Gallery`, `dyl:Win.Grow="1"`) can be resized by its borders, maximized and snapped by Windows, never minimized, its lists taking the height and the width it has more or less (the fixed `Width` and the fixed `Grid` column that hold them, or the column marked `dyl:Win.Grow="1"`), never narrower than its content, but for a column (or a panel) given a `MinWidth` below its `Width`, which gets narrower down to it (the three columns of the Assembly Presets window, its boxes stretched to their column; a column that holds no list only gets narrower). A window too large for a screen of about 1152 x 720 even with its lists at their least is laid out again (fewer boxes one under the other, its columns given a `MinWidth`). It opens again where it was left, at its size (`DynalispWindowPlaces`, a setting of this computer: `*dyl:setslocal*`, `LocalSettings`). A window file is still written at its size, a list of a fixed `Height` (never a list without one, which would be as tall as all its items), and needs nothing else; a new window is checked with `Shots -- -fit`.
  - The rules below written for DCL keep their purpose in WPF: the same labels, the same sections, the value boxes lined up at the right of their section, the open button beside its setting.
- The windows not moved yet are DCL; the LeeMac sample module keeps its own (they are the code of Lee Mac).
- Every DynALisp window has an **Open Docs** button (exactly that label, never "Documentation"), key `docs`, next to its OK / Cancel or Close buttons. In a window file, `<Button x:Name="docs" Content="Open Docs"/>`, its page named on the `Window` (`dyl:Win.Docs="Group\Page.htm"`); in DCL:
  `: button {label = "Open Docs"; key = "docs"; width = 12; fixed_width = true;}`
- After `new_dialog`, `(Dyl:DocsTile "Group\\Page.htm")` makes it open the page (relative to `Modules\Dynalisp\Docs`, or a full path): the window stays open, and the button is greyed out when the page is missing. The windows of the core use the pages of `Docs\Core`.
- A new window comes with its docs page. Small Yes/No and name prompts have no button.
- In a group of parameters, every **value box** (edit box, popup list) ends at the same distance from the right border of the group:
  - Each value is a `row` of its own, the box last in the row.
  - A box with a label and an `edit_width`, not fixed, is right-justified in the space of its tile.
  - A box after a checkbox is `fixed_width = true`, and the checkbox (a `width`, not fixed) takes the rest of the row.
  - Two values never share a row.
- A group divided into sub-sections has a **dividing line**, drawn like the borders of the groups, over the title of each one (a `text` ending with `:`, such as *Layer key overrides:*):
  `: image {key = "..."; height = 0.8; fixed_height = true; color = -15;}`
  After `new_dialog`, `(Dyl:LineTile key)` (Docs region of `dynalisp.mnl`) draws it.
  A sub-section at the top of a column of the group has its title only, without the line: the border of the group is just above it.
  The two columns of a group are divided by the same line, vertical, between them (an image narrow and as tall as the columns, drawn by `Dyl:LineTile` too):
  `: image {key = "..."; width = 2; height = 1; fixed_width = true; color = -15;}`
- The rows of a group are **dense and balanced**. A group as tall as its neighbours never spreads its extra height between its rows:
  - Each sub-section is a `: column { fixed_height = true; ... }`, its dividing line and title included.
  - A `: spacer { }` between the sub-sections takes the extra height, spread evenly, and the last row ends at the bottom of the group.
  - A group without sub-sections ends with that spacer instead.
- Adding or removing a parameter **rebalances the window**:
  - The columns of groups stay about the same height. When one gets taller by more than a couple of rows, a sub-section moves to the shorter column if it fits there. When the groups no longer balance side by side, they go one under the other, each split in two columns: the basic settings and the layer key overrides on the left, the optional settings on the right (the Hatch settings of the Hatch Presets window).
  - The list heights and the docs follow.
- The **view choices** of a window (the sort of its list, the group it shows) are not settings: they stay in the window, never in the Settings window. They are kept for the session, or, with a **Set default** button beside them, saved as the one the window opens on: a `Dynalisp*` user setting of the tool (`DynalispPresetShow<tool>` for the Show group of the preset windows), off (All) until the user sets it.
- A window that lists items and edits the selected one (presets, materials, layer keys, rules...) lets **several items be selected** in its list (`multiple_select = true`, `SelectionMode="Extended"` in WPF; Ctrl / Shift click), to edit them at once:
  - The fields show the item clicked first (the one shown). A value changed is given to every item selected; their other values are left as they are.
  - A value unique to each item (name, key), Copy, and the values edited line by line (a list of layers) are for one item only: greyed out while several are selected. Delete and Reset act on every item selected.
  - The heading of the fields gives their number (*Parameters (3 selected)*; in a preset window, the status under the name: *3 presets selected*).
  - The code keeps the item shown (`pst:idx`) and the items selected (`pst:sel`). A field's action gives its value to all of them (`Remote>>Dyl:PresetDlgPut`); committing the fields (before changing the selection) writes the item shown only.
  - A window that edits through an *Add* button (a value typed for one item, as System Variables) lets several be selected to Remove them at once.
- A button beside a setting that opens the window editing it (a sub-window, the AutoCAD color dialog...), or the file it comes from (the `.pat` file of a pattern), is the square **open button** of the Settings window, never a `...` button. It goes just to the left of the value box it edits:
  `: image_button {key = "..."; height = 1; fixed_height = true; aspect_ratio = 1; fixed_width = true; color = -15;}`
  In a window file, `<dyl:OpenButton x:Name="..."/>`, greyed out by a rule (`dyl:Win.EnabledBy`).
- After `new_dialog`, `(Dyl:MoreTile key on)` (Docs region of `dynalisp.mnl`) draws its *open* icon. To grey it out or turn it back on, call it again with `on` nil or true in place of `mode_tile`, since `mode_tile` leaves the icon black. A button that does something else keeps a text label (*New...*, *Edit layer keys...*, *Pick...*).

- Windows are **minimal**, for a clean, modern look that is easy to approach: the fewest graphics, text and boxes that do the job.
  - Labels and list items are short, **never with text in parentheses** explaining them (*Sides*, not *Sides (Polygon)*; *Linear*, not *Linear (band along a line)*; *Transparency*, not *Transparency (0-90)*), and no description line under a field. The details are in the docs page that **Open Docs** opens.
  - What can be set is shown by the window itself: a value the current choice does not use (the method of a preset, a checkbox off) is greyed out, never explained.
  - A marker that warns about a value (*(not defined)*, *(missing material)*) is not an explanation: it stays.
  - The docs name each setting with its label, and explain it there.
  - A choice whose items draw differently (the ends and the corners of the Band Settings window of Quick Draw) shows a **sketch of the item picked** under its list, drawn in the window file (one `Canvas` per item, shown by its `dyl:Win.VisibleBy` rule, the `Dyl.Sketch.*` styles of `Theme.xaml`), the same as the sketch of its docs page: a picture says what the item does without a word, so it is not an explanation. A sketch changed is changed in both.

*Why: a WPF window looks like the rest of Windows and its picture is drawn from its file, without AutoCAD; a window as large as its content ran off a small screen (or one at a large display scale), its OK out of reach, and a list of a hundred presets is read better in a window the user makes taller, as in the Explorer of Windows, kept where they left it; a window file without code keeps the Lisp in charge, as with DCL; a preset window answers each click at once, since it never waits for the Lisp, and the Lisp still has the last word on what is saved; every window leads to its documentation, a list is shown the way the user picked it where the list is (and opens that way again once set as the default), a setting that opens its own window looks the same in every window, the values of a group read as one column, its sub-sections look like the groups, a window stays balanced as it changes, many items get the same change in one go, and a window is read at a glance, its explanations kept in one place, the docs, its sketches matching theirs; a search, or a row filling its boxes, answers as it is typed or clicked, so the window closes only for what the Lisp must do; the windows that set up the drawing tools are used together (a preset, its assembly, its material, the hatch of that material), so they are the tabs of one window, each one still its own file and its own Lisp, and a tab left is saved so the next one shows what was just made in it; the Manager stays open while the user draws, since a preset is set up while looking at the drawing, and the Lisp of its tools needs no change to be run one button at a time.*
